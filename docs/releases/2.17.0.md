# Manager 2.17.0 — AI Operations

Released 20 October 2026.

AI Operations adds incident diagnosis, database configuration assistance, reviewed application recovery and 30-day sampled uptime. Open **Infrastructure → AI Operations**. Alerts remain inside Manager.

## Diagnosis and connection

Local diagnosis works immediately from the existing independent monitor and unified alerts. Administrators can enable an optional OpenAI connection with an API project key and a model ID available to that project. The key is encrypted at rest and never returned to the browser. No credentials are borrowed from applications or other integrations.

AI analysis runs only when an operator requests it. Requests contain anonymous service references, fixed issue categories and bounded monitoring metrics. Logs, raw health responses, paths, hostnames, environment values and source code are excluded. The provider cannot invoke tools or recovery actions. Responses use a strict JSON schema, are validated again locally and are rendered as plain text. References map back to application names only inside Manager.

The connection uses the Responses API with `store: false`, a 25-second deadline, a bounded response and output limit, one concurrent request, a one-minute request interval and a maximum of 50 attempts per rolling day. These controls limit requests; they are not a currency-denominated spending cap. Provider retention policies still apply. Failure preserves local diagnosis and records a safe, generic explanation.

API references: [Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [Responses storage](https://developers.openai.com/api/docs/guides/migrate-to-responses).

## Database configuration assistance

The assistant inspects bounded regular environment files in the selected application's directory and its managed data-service assignments. It reports key presence, empty settings, primary database assignment and whether an encrypted credential exists. It does not return secret values, connect using administrator credentials, create accounts, grant privileges or rewrite configuration.

Configuration on disk may differ from runtime configuration or custom application requirements; the review states this explicitly. Existing Storage controls remain available for a separately reviewed configuration sync. Previously deferred database issues remain alerts until their actual readiness checks recover.

## Reviewed recovery

An operator can prepare a five-minute review for one confirmed application incident. The review describes the target, interruption, verification and limitations. The same operator must explicitly approve it; changing application/process/deployment/health-profile identity invalidates the review. Healthy, stopped, missing, ambiguous, database-failing or Manager processes are blocked. Stale monitoring and shared critical infrastructure incidents also block recovery.

Execution rechecks readiness and identity, acquires a project operation lock and a global recovery lock, checks conflicting jobs, enforces a 30-minute attempt cooldown, and persists its audit entry before restarting one numeric PM2 process ID. Direct RPC connects to the existing daemon and cannot launch another daemon. Environment, release, saved process list and shared configuration are unchanged.

Two consecutive readiness successes and an unchanged inventory of other processes are required for success. A restart cannot be undone. Failures stop further attempts, remain in Operations history and produce an in-deployer alert requiring review. An attempt without verification after ten minutes is shown as interrupted. Administrators can pause all reviewed recovery. No unattended repairs are enabled.

## Sampled uptime

The independent monitor records one minute slot per service, retaining 30 days in a separate `uptime.json` beside monitor state. Collection shares the existing exclusive monitor lock and uses atomic writes. Corrupt uptime history is preserved and produces a collector alert.

The 24-hour, seven-day and 30-day views distinguish successful, failed, unknown, missing and intentionally paused observations. Coverage includes the entire selected window; earlier history is not invented. A 99.9% sampled readiness target is assessed only with at least 99% check coverage. This is not a guarantee of availability or a measurement of every user request, DNS, public TLS or external network access.

## Rollout and rollback

Build and validate in an isolated checkout. Keep provider analysis disabled until an administrator configures it. No application database changes or application restarts are needed to activate this release.

Before restarting Manager, verify that deployments, backups, migrations, runtime installs, cron jobs and Operations requests are idle. Retain the prior source, dependencies and compiled build together for rollback. Install new monitor dependencies before replacing its entry point. The additive Operations tables and uptime history can remain if Manager is rolled back; do not overwrite current observations.
