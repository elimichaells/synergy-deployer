# Server Manager (PM2 + GitHub)

Centralized server management for multiple projects on a single host. This build targets:

- Single server
- GitHub-based deployments
- PM2 for runtime
- Multi-user roles (admin, operator, viewer)

## Windows Server Package

Manager ships with a graphical Windows setup executable plus the preflighted
PowerShell package used for unattended and recovery installations.

    powershell -ExecutionPolicy Bypass -File .\scripts\package-manager-exe.ps1
    powershell -ExecutionPolicy Bypass -File .\scripts\package-manager.ps1
    .\setup.cmd
    .\setup.cmd -Unattended -Plan
    .\setup.cmd -Unattended

The self-elevating setup launcher requires only 64-bit Windows Server and an
internet connection. It installs Git, Node.js LTS, the latest npm compatible
with that Node release, PM2, PostgreSQL, Caddy, Pgweb, and selected Go, PHP,
Composer, or database runtimes. Operators do not need to configure packages or
services before setup, and the installer never opens database ports.

`ManagerSetup.exe` defaults to its verified embedded package, so a new server
does not need access to a GitHub release. Internet is still required to install
dependencies. Optional online installation can select `latest` or a specific tag from GitHub Releases and accepts an in-memory token for
private repositories, verifies the release SHA-256 manifest, and runs the
read-only server preflight before enabling installation. The same executable
offers a direct switch to the embedded package if GitHub cannot find an accessible release (404).
Target servers do not need .NET because the setup executable is self-contained.
Automatic setup supports either MySQL or MariaDB on a host. The wizard makes
these choices exclusive and preflight checks existing services before installing
anything, preventing the MariaDB package from colliding with MySQL. Separately
configured instances of both engines can still be registered in Data services.
MySQL setup verifies the Windows server service and its loopback listener,
rather than treating `mysql.exe` as an installed server. It recognizes custom
service names and can register a missing service from existing server binaries
and configuration. Repair reuses initialized data; only an empty data directory
is initialized, and incomplete non-empty directories are left for inspection.
Package and executable SHA-256 manifests record the source commit and whether
the checkout contained uncommitted changes when packaged.
Release assets are generated by `npm run package:windows:exe`; tag pushes can
publish them through `.github/workflows/manager-release.yml`.

By default, setup creates two isolated PostgreSQL clusters:

- Manager control PostgreSQL on `127.0.0.1:5432`, reserved for Manager data.
- Managed application PostgreSQL on `127.0.0.1:5433`, registered as the
  recommended project provider.

Every PostgreSQL project service receives its own database, non-superuser role,
encrypted credential, deployment environment variables, and configurable
daily, weekly, monthly, or yearly backup schedule. Critical projects can use a
separately registered dedicated provider. Neither PostgreSQL port is opened in
Windows Firewall.

After installation, use **Data services** to register PostgreSQL, MySQL,
MariaDB, SQL Server, MongoDB, or Redis infrastructure and provision several
named resources per project. Use **Domains & SSL** for scoped Cloudflare
connections, DNS records, proxy state, Caddy routing, and explicit Full
(strict) SSL changes.

Manager itself continues to use PostgreSQL as its control-plane store. Project
applications are not restricted to PostgreSQL.

## Legacy Quick Start

### One-command bootstrap (new server)

Prerequisites:
- Node.js + npm
- PM2 (`npm i -g pm2`)
- PostgreSQL running and reachable
- Caddy binary at `C:\web\caddy.exe`

Run:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\bootstrap-manager.ps1 `
  -ManagerDomain deploy.example.com `
  -AdminEmail admin@example.com `
  -AdminPassword 'StrongPassword!123' `
  -DbPassword 'your-postgres-password'
```

This command will:
- write `.env.local`
- apply `db/schema.sql`
- create/update an admin user
- create/update `C:\web\Caddyfile` with the manager domain block
- start `manager` and `caddy` under PM2 and persist with `pm2 save`

### Manual setup

1. Install dependencies

```bash
cd C:\web\manager-v2
npm install
```

2. Configure environment

Create `.env.local`:

```env
JWT_SECRET=change-this-secret
DATABASE_URL=postgres://postgres:password@localhost:5432/server_manager
GITHUB_TOKEN=ghp_xxxxx
PRODUCTION_PATH=C:\\web\\production
```

3. Create database schema

```bash
psql "%DATABASE_URL%" -f db/schema.sql
```

4. Create the first admin user

```sql
insert into users (email, name, password_hash, role)
values ('admin@local', 'Admin', '$2b$12$REPLACE_WITH_BCRYPT', 'admin');
```

Generate a bcrypt hash:

```bash
node -e "console.log(require('bcrypt').hashSync('your-password', 12))"
```

5. Run the app

```bash
npm run dev
```

Open `http://localhost:4000`.

## Project Registration Fields

- `name`: Display name
- `repoUrl`: GitHub HTTPS clone URL (optional)
- `defaultBranch`: Defaults to `main`
- `rootPath`: Local path where repo is cloned
- `installCmd`: e.g. `npm install`
- `buildCmd`: e.g. `npm run build`
- `startCmd`: e.g. `npm start`
- `pm2Name`: Process name in PM2
- `port` + `url`: Optional metadata

If `startCmd` begins with `npm`, deployments will use:

```
pm2 start npm --name "<pm2Name>" -- <startCmd-without-npm>
```

## Notes

- The deployment pipeline runs on the same server as this app.
- For private GitHub repos, set `GITHUB_TOKEN`.
- Roles:
  - `admin`: full access
  - `operator`: create projects + deploy
  - `viewer`: read-only
 - Auto-register looks under `PRODUCTION_PATH` and adds any missing folders as projects.
